# CLAUDE.md — The RGB (Reality Generation Box)

## What This Is

The RGB is a **self-contained rendering and intelligence engine** that players cross into. It sits between a host game's state and the player's LLM. Its first deployment is inside Space Tower, but it is designed to be portable — any game can feed context in and get AI-powered experiences out.

This repo (`space-tower-rgb`) contains the RGB engine: 3D environments, LLM connection, NPC conversation system, scenario management, procedural rendering systems, and the "Connect Your Mind" onboarding flow.

**The RGB boundary is sacred.** The host game (Space Tower) is deterministic and handcrafted. The RGB is alive and responsive. They don't contaminate each other. You walk through doors and the world changes. That threshold is the magic trick.

---

## The Two Capability Tracks

The RGB advances two systems in parallel:

**Intelligence** — NPC conversations, scenario management, ambient storytelling. The LLM as director of human drama.

**Rendering** — Procedural visual systems the LLM can orchestrate. Lightweight, beautiful, scientifically grounded, responsive to intent. The LLM as director of what you *see*.

Each 10-floor segment of Space Tower ships a new generation of both:

- **RGB v1 (Floors 1–10):** NPC conversations + atmospheric procedurals (sky, lighting, particles)
- **RGB v2 (Floors 11–20):** Richer scenarios + physics-accurate procedural visualizations
- **RGB v3 (Floors 21–30):** The rendering IS the experience — scientific visualization
- **RGB v4+:** Portable scientific tool. Molecular dynamics, fluid simulations, astrophysics.

The long-term vision: an LLM-orchestrated rendering engine for making invisible things visible and explorable. Space Tower is the proving ground.

---

## What the RGB Does

- **Renders immersive spaces:** 3D environments powered by game context
- **Renders procedural atmosphere:** Shader-driven sky, dynamic lighting, particle systems — all parameterized for LLM control
- **Powers live dialogue:** NPC conversations generated by the player's LLM, not dialogue trees
- **Drives scenarios:** Multi-phase narrative events that escalate based on time and player behavior
- **Creates ambient life:** Environmental events, background chatter, atmospheric descriptions
- **Owns the LLM connection:** Every interaction between the player's LLM and any host game passes through the RGB

## What the RGB Does NOT Do

- Bleed into the host game's sim layer
- Control game state — it reads context in, it doesn't write back
- Require a specific host game — it accepts a generic context payload
- Run a backend — all LLM calls go directly from the browser to the player's provider
- Rely on heavy assets — rendering is math-driven, not asset-driven

The rare exception: **Mayors.** Each segment's top-floor mayor is an RGB-powered character surfaced inside the sim. The RGB provides the intelligence; the sim provides the presentation. The Keeper on Floor 10 is the first of these.

## Architecture

### The Rendering Engine (the RGB's eyes)

The rendering engine uses procedural techniques — shaders, particle systems, noise functions, mathematical surfaces — orchestrated by LLM-driven parameters. No heavy asset downloads. Visuals are generated from math every frame.

The LLM communicates with the rendering engine through a **parameter schema**:

```js
{
  atmosphere: {
    mood: 'tense',           // semantic → maps to parameter presets
    timeOfDay: 0.65,         // 0=dawn, 0.5=noon, 1=dusk
    weatherIntensity: 0.3,   // 0=clear, 1=storm
  },
  lighting: {
    warmth: 0.7,             // 0=clinical, 1=golden
    contrast: 0.6,           // 0=flat, 1=dramatic
    focusPoint: [x, y, z],   // where the eye is drawn
  },
  particles: {
    systems: ['dust_motes', 'kitchen_steam'],
    intensity: { dust_motes: 0.4, kitchen_steam: 0.7 }
  },
  sky: {
    gradient: ['#1a1a2e', '#16213e', '#0f3460'],
    cloudCover: 0.3,
    dynamism: 0.5
  }
}
```

This schema is extensible. v1 uses it for atmosphere. v2 adds physics parameters. v3 adds scientific visualization parameters. Same interface, expanding vocabulary.

### The LLM Connection (the RGB's nervous system)

The RGB supports two connection paths, both feeding into a single unified `chat()` function:

**Path 1: OpenRouter (recommended, default)**
- Unified API gateway: one account, one key, 500+ models
- OAuth PKCE flow: "Sign in with OpenRouter" button
- Manual key paste as fallback
- Model switching within the RGB
- OpenRouter is independent (founded by Alex Atallah, ex-OpenSea CTO)
- Not affiliated with OpenAI, Anthropic, or any AI lab

**Path 2: Direct API Key (advanced)**
- OpenAI-compatible endpoints (OpenAI, Groq, Together, Ollama, LM Studio)
- Anthropic API (thin adapter for different JSON shape)
- No middleman, no markup
- Player enters endpoint URL, API key, model name

Both paths store credentials in localStorage under `rgb_llm_connection`. Credentials persist across sessions but are never transmitted anywhere except the player's chosen provider.

### Data Flow

```
Host Game (e.g. Space Tower)
    → passes context payload into RGB
The RGB
    → builds system prompts from context + NPC definitions
    → sets rendering parameters from context + scenario phase
    → sends messages to player's LLM via configured connection
    → returns NPC responses to the 3D environment
    → updates atmosphere in real time
```

The RGB never imports or depends on Space Tower's internals. It accepts a generic context object.

### NPC System

- Each NPC is a separate conversation instance with its own system prompt and history
- No cross-character awareness — NPCs don't know what the player said to others
- The player carries information between characters (this IS the social gameplay)
- System prompts follow a 7-part structure: Identity, Speech Style, Knowledge, Secret, Setting, Game Context, Rules
- Conversations are ephemeral — they exist for the duration of a visit, then reset

### Scenario System

- Scenarios are multi-phase narrative arcs with timed escalation
- Phase transitions update NPC `scenarioContext` in their system prompts
- Phase transitions ALSO update rendering parameters (lighting, particles, atmosphere)
- Time-based advancement for MVP; event-driven refinement later
- "The Critic" is the first scenario (5 phases, 4 NPCs, ~15 minutes)

## Public API (what host games import)

```js
import RGB from 'space-tower-rgb';

RGB.isConnected()                        // Is an LLM configured?
RGB.showConnectionUI()                   // Present "Connect Your Mind" modal
RGB.init(context)                        // Hand off game state, boot scenario + atmosphere
RGB.createConversation(npcConfig, ctx)   // Start an NPC conversation
RGB.chat(conversationId, message)        // Send a message
RGB.startOAuth(callbackUrl)              // Begin OpenRouter OAuth
RGB.handleOAuthCallback()               // Handle OAuth redirect
RGB.getAtmosphere()                      // Current rendering parameters
```

The host game passes in a context object. The RGB handles everything else.

### Expected Context Shape

```js
{
  litFloors: number,
  satisfaction: number,        // 0-100
  hunger: number,              // 0-100
  politicalPower: string,      // 'low' | 'rising' | 'dominant' | etc.
  floor8Outcome: string|null,  // 'builders' | 'suits' | 'negotiated'
  hasVisitedRestaurant: boolean,
  totalPlayTime: number,       // minutes
  recentModules: string[],     // last 5 things built
  npcsTalkedTo: number
}
```

This context feeds both NPC system prompts (as natural language) and rendering parameters (as atmosphere settings). A thriving tower = warmer light, more ambient life. A struggling tower = muted, sparser.

## First Deployment: Space Tower Floor 5

The restaurant on Floor 5 of Space Tower. An observation deck restaurant ~15 meters up, floor-to-ceiling glass walls, city visible below. Warm daylight, concrete floors, steel ceiling beams.

**The Critic scenario:** A food critic (Margaux Bellefleur) arrives unannounced. The manager panics. The chef doesn't know yet. 5-phase escalation over ~15 minutes. Full character definitions in `src/npcs/critic-scenario.js`.

**Purpose of the visit:**
1. Hunger refill (the player came because they need to eat)
2. Political presence (being seen boosts political power)
3. RGB threshold (while eating, the AI scenario unfolds)
4. BYOK payoff (the NPC across the table is powered by the player's own LLM)

## Design Principles

- **Discovery over instruction.** "Connect your mind" — not "Configure API settings."
- **Character dignity.** Every NPC is a person. The system prompts enforce this.
- **The RGB boundary is sacred.** This engine lives on its side of the door.
- **The atmosphere is the first character.** Before anyone speaks, the room tells you something.
- **Lightweight is a feature.** No heavy assets. Math and light. Runs everywhere, loads instantly, changes in real time.
- **Player autonomy.** OpenRouter for ease, direct key for control. Player chooses.
- **BYOK as culmination.** Connecting your LLM is a narrative moment, not a settings page.
- **The RGB is portable.** Nothing depends on Space Tower's internals.
- **Time capsule.** Each segment ships with the RGB as it exists. Segment 1 = 2026 AI + 2026 procedural rendering.
- **Scientific accuracy is aspirational, not decorative.** When the RGB visualizes physics, it should be correct physics.

## Guardrails

- No sexual content beyond PG-13
- No real violence — arguments, shouting, thrown napkins at most
- No slurs or hate speech
- Characters cannot ask about the player's real life
- No gaslighting or psychological pressure
- Boundary pushing → realistic social disapproval ("I'm going to have to ask you to leave")
- Death is slapstick only → fade-to-black, respawn, zero game consequence
